| ID | Topic | Adopted decision |
|---|---|---|
| LAB-D01 | Staff Lab list behavior | Use the sourced Courses & Labs page for HOD/Manager and My Labs/Assignments for Students. Staff list shows Lab title, Course, Problem, status, scope, max score, due date and updated time. Filters: Course, status, scope, Group and due-date range where permitted. Default sort updatedAt descending then id; page size 20, max 100. Exact route strings/control copy remain UX-owned. |
| LAB-D02 | Title and description | Title is required, trimmed, non-empty and 3–255 characters. Description is optional plain text with a configurable platform limit; empty description is allowed. System IDs/timestamps are not client-editable. |
| LAB-D03 | Problem cardinality | One Problem per LabAssignment in v1, matching the conceptual `problemId` field. Multi-Problem Labs are deferred; create separate LabAssignments for separate Problems. |
| LAB-D04 | Maximum score | maxScore is a required positive integer. No bonus score is supported; Lab score cannot exceed maxScore. A configurable platform ceiling is enforced consistently with score storage precision; no arbitrary clamp. |
| LAB-D05 | Group assignment | Group assignment is optional and may include multiple Groups through GroupLab. With no GroupLab links, eligible enrolled Students within Course/Lab scope can access. Where GroupLab links exist, membership in at least one assigned active Group is an additional requirement. GroupLab writes belong to Module 10. |
| LAB-D06 | Role actions and Manager Delete | SUPER_ADMIN: platform-wide manage. HOD: create/view/update and lifecycle control within College+Department. MANAGER: view/create/update within assigned College+Department+Section/permitted Group, SECTION_ONLY only; no Delete, publish, close, archive or scope widening. FINANCE_TEAM: College-scoped metadata-only View. STUDENT: eligible Lab view, own submit and own result. No hard-delete API. |
| LAB-D07 | Evaluation-to-Lab score formula | For a complete Module 7 evaluation, `LabScore = round2(EvaluationScorePercent × maxScore / 100)`. Module 7 owns evaluation percentage/verdict; Module 8 owns conversion only. A completed code-failure evaluation can earn partial/zero Lab score according to Module 7 percentage. Infrastructure/incomplete evaluation has no final Lab score. |
| LAB-D08 | Score precision and rounding | Persist LabSubmission.score as DECIMAL(12,2); round half-up once when finalizing the Lab score. Preserve the exact Module 7 integer percentage and the maxScore snapshot used in the calculation. Never round at intermediate display/conversion steps. |
| LAB-D09 | Due date and late policy | dueDate is optional. Default when set: hard cutoff; accept submissions received at or before dueDate and reject later requests. A Lab may explicitly use ACCEPT_NO_PENALTY to accept late submissions and mark them late. No automatic penalty, grace period or penalty formula in v1. |
| LAB-D10 | Lab status field | Add a LabStatus field because LabAssignment has no status field in the source schema. Values: DRAFT, PUBLISHED, CLOSED, ARCHIVED. CLOSED is an operational state extension; it is not present in the source PublishStatus enum. |
| LAB-D11 | Lifecycle transitions and delete | Transitions: create→DRAFT; DRAFT→PUBLISHED; PUBLISHED→CLOSED; CLOSED→PUBLISHED (reopen); DRAFT/PUBLISHED/CLOSED→ARCHIVED; ARCHIVED→DRAFT (restore). HOD/SUPER_ADMIN control lifecycle. CLOSED blocks new attempts but preserves reads; ARCHIVED is history-only. No hard deletion or cascade. |
| LAB-D12 | Edits after publication/submission | Published Lab configuration is immutable for grading. Changes to Course, Problem, ProblemVersion, scope, Group targets, maxScore, dueDate, availability or attempt policy create a new LabAssignmentRevision and republish. Existing LabSubmissions remain pinned to the prior revision and are not silently recalculated. |
| LAB-D13 | Problem version at publish/submit | Each published LabAssignmentRevision pins one immutable, published ProblemVersion from the same College. CodeSubmission must reference that same ProblemVersion. New Problem versions require a new Lab revision; queued submissions and rejudge use the pinned original version. |
| LAB-D14 | Course/Section/Group eligibility precedence | New attempts require an active Student, active College, PUBLISHED Course, active Course entitlement under Module 3, CourseEnrollment.status=ENROLLED, CourseSection/Section inclusion, and intersection of Course, Lab and Problem scopes. If GroupLab rows exist, Student must also be a member of an assigned active Group. Group membership never substitutes for CourseEnrollment. |
| LAB-D15 | Group membership changes | Current membership is checked on every new Lab list/detail/submit request. A Student joining an assigned active Group after publication gains access when all other eligibility checks pass. Removal from a Group immediately blocks new attempts but preserves the Student’s own prior Lab history as read-only while the account remains active. |
| LAB-D16 | Group assignment vs collaborative submission | Group membership only determines eligibility. Each Student has an individual CodeSubmission, LabSubmission, attempt count and score. Shared/collaborative Group submissions and shared scores are out of v1. |
| LAB-D17 | Lab completion | Progress is derived. A Student is COMPLETED when at least one accepted attempt has a complete Module 7 evaluation result, regardless of score percentage; no passing threshold or staff completion override in v1. Pending/failed infrastructure evaluation is not completion. |
| LAB-D18 | Attempts and final score | Attempts are unlimited by default; an optional positive maxAttempts may be configured per Lab revision. Count only accepted CodeSubmissions. Enforce one in-flight attempt per Student+Lab. Final/best score is the highest finalized valid LabSubmission.score; ties select the latest accepted attempt. Rejudge is not a new Student attempt. |
| LAB-D19 | CodeSubmission/LabSubmission transaction and idempotency | One accepted LAB-context CodeSubmission links to one LabSubmission. Use Module 6 Idempotency-Key and atomic attempt allocation; create the LabSubmission link in the same database transaction where feasible. Otherwise consume a durable accepted-submission outbox event with unique codeSubmissionId and Module 18 reconciliation. Retries must not create duplicate attempts. |
| LAB-D20 | Rejudge permission, attempt and version | Rejudge follows Module 6/7: SUPER_ADMIN only, reason required and audited; create a new SubmissionRun under the same CodeSubmission and original ProblemVersion; do not create a new LabSubmission or increment attemptNumber. |
| LAB-D21 | Rejudge score reconciliation/history | On a completed rejudge, recompute the affected attempt’s Lab score using the pinned LabAssignmentRevision and formula; append a LabScoreHistory record and recompute the Student’s best attempt. Preserve the prior score/run history. Failed/incomplete rejudge leaves the last completed score unchanged. |
| LAB-D22 | Manual score override | Manual score adjustment is disabled in v1. HOD/Manager CRUD/View does not imply grade override. Do not expose override controls/endpoints until a distinct permission, reason, provenance, approval and history policy is approved. |
| LAB-D23 | Result visibility and privacy | Student reads own LabSubmission, score, feedback and safe Module 7 result only. Visible testcase feedback follows Module 7; hidden test details, raw Judge0 tokens/payloads and other Students’ code/results are never exposed. HOD/Manager see scoped Lab performance summaries and permitted feedback, not raw source or hidden/raw JudgeRun data. SUPER_ADMIN raw inspection follows audited Module 6/7 controls. Finance sees no Student-level academic data. |
| LAB-D24 | Audit and notification boundaries | Module 15 owns canonical audit. Record Lab create/update/publish/close/archive/restore, Group/Section assignment changes, feedback edits and score recomputation with actor, target, scope, action, timestamp and reason/source event. Module 13 owns notification delivery; Lab emits safe committed events only. No source, hidden testcase data or Judge0 token in ordinary events. |
| LAB-D25 | CodeSubmission–LabSubmission cardinality | Adopt one-to-one for a single Lab-context CodeSubmission and its LabSubmission link (`LabSubmission.codeSubmissionId` unique). The conceptual ERD depicts CodeSubmission→many LabSubmission, but Module 6 assigns each CodeSubmission exactly one context/contextId; a LAB context points to one LabAssignment. Each attempt is a separate CodeSubmission/LabSubmission pair. Record this source/schema discrepancy for migration. |
| LAB-D26 | Persist or derive Lab score | Persist the current effective per-attempt score in LabSubmission.score, as the conceptual schema provides. Derive Student best/final score from finalized attempts. Append-only LabScoreHistory records score changes caused by rejudge/reconciliation; do not duplicate Module 7 testcase scoring. |
| LAB-D27 | Score/revision snapshots | Add LabAssignmentRevision and pin it on each LabSubmission. Snapshot ProblemVersion, maxScore, dueDate, availability, scope, late policy and attempt policy. Score calculation uses that revision; edits/new Problem versions never retroactively change an existing score. Rejudge remains on original revision/version. |
| LAB-D28 | Feedback visibility and validation | Feedback is optional plain text, up to 10,000 characters after trimming. HOD/Manager can add/edit it for scoped LabSubmissions; Students can read their own feedback only. Blank input clears feedback. Changes are audited; Module 13 may notify according to notification configuration. |
| LAB-D29 | Deadline timestamp/timezone | Store and compare UTC timestamps. dueDate is inclusive: server-received submission time `<= dueDate` is on time. Student UI converts UTC to local display time. Client clocks and Judge0 completion time never determine lateness. |
| LAB-D30 | Individual deadline extensions | Per-Student extensions are not supported in v1. A global due-date change requires a new LabAssignmentRevision and republish; existing LabSubmissions retain the original revision/deadline. |
| LAB-D31 | Authoritative submission timestamp | Use the trusted server ingress/acceptance timestamp from the Module 6 submission intake. Copy that timestamp to LabSubmission.submittedAt/acceptedAt; ignore client-supplied timestamps for grading or deadline decisions. |
| LAB-D32 | ContentScope inheritance | Use the adopted Module 4/5 semantics: SECTION_ONLY targets explicit Sections; DEPT_WIDE includes active Sections in the owning Department; GLOBAL includes active Sections in the owning College and is SUPER_ADMIN-only. Effective Lab eligibility is the intersection of Course scope, Lab scope, Problem scope, Section/Group assignment and active enrollment; no link/flag may widen another scope. Add LabSection for explicit Lab Section targeting where needed. |
| LAB-D33 | Progress persistence | Do not add a separate LabProgress percentage/table in v1. Derive NOT_STARTED, SUBMITTED, EVALUATION_PENDING, COMPLETED and EVALUATION_FAILED from LabSubmission/CodeSubmission/SubmissionRun. CourseEnrollment.completedAt is not Lab completion. Display best score and latest attempt separately. |
| LAB-D34 | Manual override vs rejudge precedence | Manual override is disabled in v1, so rejudge is the only score recomputation path. A completed rejudge updates the affected attempt and best-score projection with history. Do not silently layer a manual override onto an automated score. |
| LAB-D35 | Audit/outbox failure behavior | Commit Lab mutation/submission/score state with a durable outbox event. Delivery is at-least-once and consumers dedupe by eventId/sourceRunId. Notification failure does not roll back a committed Lab operation; retry/reconciliation follows Modules 13/18. Required privileged audit actions fail closed if audit cannot be durably recorded. |
| LAB-D36 | Finance Team visibility | FINANCE_TEAM receives College-scoped metadata-only Lab View (title, Course/Problem metadata, status, maxScore and due date). It receives no LabSubmission, Student identity/performance, score, feedback, source code, raw evaluation or Group member details. |
| LAB-D37 | Faculty/Lab Staff role | Do not introduce a separate Faculty/Lab Staff role in v1. “Lab Staff” is a page label, not a role in the source RBAC list. Use HOD and scoped MANAGER permissions. |
| LAB-D38 | Page names and route/control detail | Use source page labels: HOD/Manager Courses & Labs; Manager Student Performance; Student Dashboard, Assignments, My Labs and My Groups. Exact URL routes, control copy and layout are UX/implementation details not established by source. |

## Source reconciliation
- Business Flow v2 and original show Group → Lab → Problem → Student submission → CodeSubmission → Judge0 → Evaluation → Lab Score. The flow does not specify whether submissions are collaborative.
- The conceptual schema defines one `courseId` and one `problemId` on LabAssignment; LabSubmission carries `studentId`, `codeSubmissionId`, score, feedback and submittedAt; GroupLab links Groups and Labs. It does not define Lab lifecycle, attempt policy, late policy, progress or score history.
- The RBAC platform matrix grants Manager Full CRUD* for Labs, while the page/API matrices show V/C/U* without explicit Delete. Adopted least privilege denies Manager Delete. Finance’s broad View is limited to College metadata; no Student-level academic data is exposed.
- The source ERD depicts CodeSubmission→many LabSubmission, but Module 6 gives a CodeSubmission exactly one activity context/contextId. For LAB context, Module 8 adopts one LabSubmission link per CodeSubmission, with each Student attempt represented by a separate CodeSubmission/LabSubmission pair.
- The legacy audit states the dedicated Lab subsystem was absent from the audited snapshot. That finding does not establish target behavior and does not invalidate the conceptual schema or module intent.
- Module 4 owns Course/Section/Enrollment and ContentScope eligibility; Module 5 owns immutable ProblemVersion/TestCase; Module 6 owns CodeSubmission/SubmissionRun/JudgeRun and idempotency; Module 7 owns evaluation percentage/verdict and hidden-data policy; Module 10 owns Group membership and GroupLab writes; Modules 13/15/17/18 own notifications, audit, state transitions and recovery.
