# Module 9 — Assessments: Adopted Decisions

**Document ID:** DEZ-ASMT-DECISIONS-009  
**Version:** 1.0  
**Status:** Adopted target product baseline  
**Decision range:** ASMT-D01–ASMT-D36  
**Cross-module basis:** Modules 4–8, Module 10 Groups, Modules 13/15/16/17/18.

Adopted by the user's direction to proceed using the established recommended-default approach. Conceptual source fields and legacy audit observations remain distinct. The legacy implementation is historical evidence only. README Sections 26–31 and the adopted contract in FUNCTION-SPECIFICATIONS.md are normative.

| ID | Topic | Adopted decision |
|---|---|---|
| ASMT-D01 | Role and action permissions | SUPER_ADMIN has global manage. HOD has create/view/update/publish/archive within assigned College+Department. MANAGER has view/create/update only within assigned College+Department+Section/permitted Group and may author drafts; no publish/archive/delete. FINANCE_TEAM has no Assessment access. STUDENT has view/attempt and own-result access subject to release. |
| ASMT-D02 | Assessment type | CODING is the only AssessmentType supported in v1, matching the conceptual enum. MCQ, quiz, viva/rubric and non-coding question types are out of scope. |
| ASMT-D03 | Multi-Problem model | Use the conceptual AssessmentProblem junction. One Assessment revision contains one or more Problems; legacy scalar `problemId` is historical only and is not target cardinality. |
| ASMT-D04 | Problem ordering and duplicates | AssessmentProblem orderIndex is zero-based, unique and contiguous per published revision. Duplicate Problem IDs within one revision are rejected. Randomized order is not supported in v1. |
| ASMT-D05 | Problem weights and requiredness | All linked Problems are required and equally weighted in v1. No Problem weight, optional flag, bonus points or per-Problem max score is added. Problem-level evaluation percentage is normalized by Module 7. |
| ASMT-D06 | Audience model | Assessment belongs to one College and Department. Use an optional single `groupId` and an `AssessmentSection` junction for explicit Section targeting. Without Section rows the audience is all active Sections in the owning Department. No individual Student assignment or multi-Group junction in v1. |
| ASMT-D07 | Student eligibility | Start requires active Student membership, active College, active Section in the Assessment's College/Department, and membership in the assigned Group when groupId is set. No CourseEnrollment requirement is inferred because the conceptual Assessment has no courseId. |
| ASMT-D08 | Group/Section membership changes | Eligibility is rechecked at list/detail/start. A Student who joins an eligible Section/Group after publication may start while the window remains open. Removal blocks new starts but does not invalidate an already-started attempt; own history remains read-only. |
| ASMT-D09 | Assessment lifecycle | Use source PublishStatus values DRAFT, PUBLISHED, ARCHIVED. Create as DRAFT; Students cannot discover DRAFT; PUBLISHED is schedule/eligibility-gated; ARCHIVED is history-only and blocks new starts/submissions. No separate CANCELLED/EXPIRED persisted enum in v1. |
| ASMT-D10 | Lifecycle authority and deletion | SUPER_ADMIN/HOD may publish/archive/restore; MANAGER may create/update drafts only. Archive is soft retirement; restore returns to DRAFT. No hard-delete endpoint or cascade of attempts/results. |
| ASMT-D11 | Published revisions | Each publish creates an immutable AssessmentRevision snapshot of settings, audience and ordered AssessmentRevisionProblem set. Editing published settings/problems creates a new draft revision and republish; active and historical attempts stay pinned to their original revision. |
| ASMT-D12 | Problem version snapshot | Every AssessmentRevisionProblem pins one published immutable Module 5 ProblemVersion from the same College. All CodeSubmissions and re-evaluations use that pinned ProblemVersion, even if a newer Problem version is published. |
| ASMT-D13 | Problem editing and association | Problem add/remove/reorder and changes to scope, passingPercentage, duration, attempts, dates, audience, result policy or integrity settings are revisioned. Published revision content is never mutated in place. |
| ASMT-D14 | Schedule window | startsAt and endsAt are optional UTC timestamps. If startsAt is null, PUBLISHED Assessment is immediately startable; if endsAt is null, there is no global close. When both exist startsAt must be earlier than endsAt. |
| ASMT-D15 | Attempt duration and server clock | durationMinutes is positive and applies per AssessmentAttempt from server-accepted explicit Start. Browser timer is display-only. Assessment deadline is min(startedAt + durationMinutes, revision.endsAt when present). Assessment duration is never passed as Judge0 CPU/memory limit. |
| ASMT-D16 | Start/expiry boundary and autosubmit | Start is allowed at/after startsAt and strictly before endsAt. Submissions are accepted through the inclusive attempt deadline (`receivedAt <= deadlineAt`). At expiry the attempt locks; no browser-only auto-submit or implicit submission of unsent editor code occurs. Only accepted CodeSubmissions are graded. |
| ASMT-D17 | Expiry and unanswered Problems | Student may explicitly Finish early. At Finish/deadline, unsubmitted Problems receive 0 for attempt aggregation. Submitted Problems wait for terminal Module 7 results. Pending/unknown/infrastructure failures do not become zero; attempt remains FINALIZING/RECOVERY_REQUIRED until reconciled. |
| ASMT-D18 | AssessmentAttempt model and attempt consumption | One AssessmentAttempt represents a complete multi-Problem session. Create it transactionally on successful explicit Start; opening details/workspace or reconnecting does not consume an attempt. Resume the same active attempt and original deadline. One active attempt per Student+Assessment. |
| ASMT-D19 | Attempt count and limit | Add maxAttempts per AssessmentRevision; default 1 and positive integer when configured. Count only committed AssessmentAttempt rows. Client counters are ignored. Attempts are not reset by rejudge or result release. |
| ASMT-D20 | Multiple submissions within one attempt | A Student may submit a Problem multiple times within the same active attempt, subject to Module 6 rate/idempotency limits. Retain every CodeSubmission; use the highest complete Module 7 percentage for that Problem, latest accepted submission as tie-breaker. |
| ASMT-D21 | Assessment attempt score aggregation | For a finalized attempt, average the selected per-Problem integer percentages equally across all Problems in the pinned revision, including unanswered Problems as 0. Round half-up once to 2 decimals. No weights, optional Problems or Contest-style penalty apply. |
| ASMT-D22 | Passing threshold | passingPercentage is required, defaults to 50.00, and must be 0.00–100.00. Attempt passes when finalized scorePercent >= passingPercentage. Equality passes. Pass/fail is not finalized while any submitted Problem evaluation is pending or infrastructure-failed. |
| ASMT-D23 | Official score across attempts | Official Assessment score is the highest finalized valid attempt score; latest started attempt breaks ties. Preserve all attempt scores/history. Do not average attempts or take latest by default. |
| ASMT-D24 | Result release policy | Add resultReleasePolicy: AFTER_CLOSE (default), IMMEDIATE_SAFE, STAFF_RELEASE. Student always sees receipt/pending state. Score/pass/attempt summary is visible only after the configured release condition. With no endsAt, AFTER_CLOSE requires explicit HOD/SUPER_ADMIN release. |
| ASMT-D25 | Student and staff result details | Student sees own released score/pass and safe Module 7 visible-case feedback only. Hidden testcase inputs/outputs/status/count/order/diagnostics remain masked. HOD/Manager see scoped roster and summary results only; no raw source/JudgeRun. SUPER_ADMIN raw access follows Modules 6/7 audited controls. |
| ASMT-D26 | Staff review and reporting | HOD can review College+Department roster/summary; MANAGER only assigned Section/permitted Group. FINANCE_TEAM is denied. Reports are read-only in v1; CSV export is not granted by the source RBAC and is disabled unless separately authorized. |
| ASMT-D27 | Re-evaluation/rejudge | Use Module 6/7 rejudge policy: SUPER_ADMIN only, reason required, new SubmissionRun for same CodeSubmission and ProblemVersion, preserve all prior runs, no new AssessmentAttempt. On completion recompute affected Problem/attempt/official scores from the newest completed run. |
| ASMT-D28 | Manual score adjustment | Manual score override is disabled in v1. Assessment CRUD/View does not imply grading permission. Corrections require a future explicit role, reason, approval, provenance and history policy. |
| ASMT-D29 | Integrity telemetry | Integrity signals are disabled by default. When enabled per revision, Student must receive clear notice; collect only tab/window blur and paste counts plus event timestamps. Signals are review-only, not proof; no automatic fail, termination, webcam, biometric or fullscreen-lock behavior. |
| ASMT-D30 | Course progress and certificates | Assessment completion/score does not automatically update CourseEnrollment.completedAt, Course progress, certificates or seat usage. Module 4 owns Course completion; Module 16 owns analytics. |
| ASMT-D31 | Notifications | Module 9 emits safe committed lifecycle, assignment, schedule reminder, attempt completion and result-release events via outbox. Module 13 owns recipient resolution, templates, channels, timing and delivery. No code, raw token or hidden testcase content in payload. |
| ASMT-D32 | Assessment sections and Groups ownership | Module 9 owns AssessmentSection targeting and Assessment lifecycle. Module 10 owns Group, GroupMember and authorized Group data; Assessment groupId must reference one active same-College/Department Group and membership checks use Module 10's canonical relation. |
| ASMT-D33 | Schema delta and score/history persistence | Add AssessmentRevision, AssessmentRevisionProblem, AssessmentAttempt, AssessmentAttemptProblem, AssessmentSection, AssessmentScoreHistory and AssessmentIntegritySignal as needed. Persist attempt-level score/pass snapshot; keep Module 7 testcase scores in its own result/run records. |
| ASMT-D34 | CodeSubmission context contract | Every Assessment CodeSubmission uses `context=ASSESSMENT`, `contextId=AssessmentAttempt.id`, and the Problem ID/ProblemVersion pinned by AssessmentRevisionProblem. AssessmentAttemptProblem correlates the submission to the ordered Problem entry. CodeSubmission remains the Module 6 canonical record. |
| ASMT-D35 | Atomicity, idempotency and recovery | Start/attempt allocation, revision publication, Problem ordering, result aggregation and outbox writes are transactional. Reuse Module 6 Idempotency-Key; dedupe Module 7 result events by eventId/runId; use optimistic concurrency. Infrastructure failures are recoverable and never masquerade as Student code failure. |
| ASMT-D36 | Audit and data retention | Module 15 audits publish/archive/restore/revision, attempt exception, rejudge, integrity review and result release. Retain academic attempt/score history under institution policy; raw source/output use configured separate retention/encryption. No automatic purge without a configured policy. |

## Source reconciliation
- Business Flow v2 establishes Student code submission through DEZOLVER backend → Judge0 → Evaluation → Result/Score. It does not define Assessment-specific session timing, multiple-Problem scoring or release rules.
- Page-to-DB Mapping v2 lists HOD/Manager Assessments and Student Assessments pages with Assessment, AssessmentProblem, Problem, CodeSubmission, User, Department and College entities.
- Conceptual Assessment fields include collegeId, departmentId, groupId, createdById, title, description, type, durationMinutes, passingPercentage, startsAt, endsAt and PublishStatus. AssessmentProblem contains assessmentId, problemId, orderIndex and createdAt.
- RBAC grants SUPER_ADMIN and HOD V/C/U/D, FINANCE_TEAM no access, MANAGER V/C/U* and STUDENT V/ATTEMPT. Manager Delete is not granted. HOD remains College+Department; Manager remains assigned Section/permitted Group.
- Legacy audit facts (global retrieval, no persisted status/window/session, client-only timer, single Problem, immediate results, broken anti-cheat cron) describe the older code only. They are not adopted target behavior.
- Modules 5–7 own Problem/ProblemVersion, CodeSubmission/Judge0 and testcase evaluation. Module 9 owns AssessmentAttempt/session orchestration, Assessment-level aggregation, pass threshold and result release.
- Module 10 owns Group and GroupMember; Module 4 owns Course/Section/enrollment. There is no Course relationship on the conceptual Assessment, so CourseEnrollment is not added as a start prerequisite.
