> These test cases operationalize the function-level QA IDs referenced by the Module 1 specification. Test fixtures are synthetic. Product decisions AUTH-D01–AUTH-D25 are approved; cases still marked decision-gated depend on cross-module implementation details or later technical/security design.

## Test fixture conventions

- Use synthetic users, colleges, departments, sections, sessions, and historical records; do not use real personal data.
- Suggested fixture labels: `COLLEGE-A/B`, `DEPT-A/B`, `SECTION-A/B`, `HOD-A`, `MANAGER-A`, `STUDENT-A/B`, `SUPERADMIN-A`, `FINANCE-A`. These are QA labels, not product enum/IDs.
- Verify both response behavior and persisted state when a test involves create/update/delete/session/status changes.
- For authorization denial, verify no restricted data is disclosed and no unauthorized mutation occurs.
- `Ready` means source-grounded behavior can be tested; `Decision-gated` means one or more linked product/security decisions must be approved first.

## Execution and sign-off

- Review test fixtures, roles, and scopes with product/security before execution.
- Execute only `Ready` cases after the relevant test environment and fixture are established.
- Do not execute decision-gated tests until the linked AUTH-D decision is approved and the specification is updated.
- Record actual result, environment/build, tester, date, evidence, and defect reference in the QA execution system; those execution fields are intentionally not invented here.
- Any behavior not supported by the approved Module 1 specification must be reported as a requirement gap, not treated as expected behavior.
